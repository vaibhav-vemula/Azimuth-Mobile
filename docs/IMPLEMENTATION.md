# Azimuth network: what is built and how it fits together

This describes the code in the repository. For the reasoning and the plan, see [DEPIN_DESIGN.md](DEPIN_DESIGN.md). For hardware status, see [STATUS_AND_RESEARCH.md](STATUS_AND_RESEARCH.md).

## Parts

| Part | Where | What it does |
|------|-------|--------------|
| App | `src/`, `App.tsx` | Expo / React Native app: Map, Chests, Radio, Satellites, Profile. |
| `rtl-sdr` module | `modules/rtl-sdr/` | Kotlin + C++ driver, spectrum, FM, and baseband recording for the RTL-SDR Blog V4. |
| `signal-scan` module | `modules/signal-scan/` | Kotlin: cellular cells, Wi-Fi and Bluetooth counts and levels, GNSS quality, venue-tag listening, and the foreground service for mapping sessions. |
| Verifier service | `server/` | Node (built-ins only, SQLite) service: checks signed reports, runs the chest and reward rules, serves the requester console. |
| Escrow program | `onchain/` | Anchor program holding bounty funds and paying nodes on the verifier's attestation. |
| Report verifier | `server/lib/verify-report.cjs` (also `tools/verify-report.cjs`) | Independent script that checks a signed report using only Node's standard library. |

## The map and the fog

The Map tab is a real street map (OpenFreeMap vector tiles, no API key) recoloured at runtime into a night-navy theme (`src/screens/map/mapStyle.ts`), because the base "dark" style is almost black and unreadable.

- **Unmapped ground** is opaque, so nothing of the map shows through it. Two looks, chosen in Settings: **Night sky** (default: deep navy with a faint nebula and scattered stars) and **Terrain lines** (topographic contours on dark ground). The images are generated by `scripts/make-fog-textures.cjs` (`assets/fog-sky*.png`, `assets/fog-terrain*.png`).
- **Clearing:** the fog clears **only while a mapping session is running**. The ground within about 60 m of you is cleared and stays cleared, shown by a dashed ring around you while mapping. Cleared ground is kept on the phone only (`explored`, in local storage) and is never uploaded. Fixes worse than 40 m, or flagged as mock locations, never clear anything. With mapping off the map still shows where you are and the ground you have already cleared, but nothing new clears.
- **The edge:** a neon rim with a soft fade and glow marks where mapped ground meets unmapped ground. It is drawn from cleared ground stored as 5 m hex cells (`src/mapping/fog.ts`): the cells are merged into one outline, traced into closed loops and smoothed, then cut out of a world-sized polygon. Small cells keep the bubble round (a bubble of big hex cells is itself a hexagon); merging avoids seams; islands of fog inside cleared ground are handled. The cells are an internal storage detail and are never drawn.
- **Mapping sheet:** a bar at the bottom of the map always shows the timer, the ground cleared this session, four live counters (towers, Wi-Fi networks, Bluetooth devices, readings) and the Start/Stop button. When a session starts the sheet rises for a moment to show there is more, and a bobbing "swipe up" hint stays until you open it. Swipe it up (or tap the handle) for a card each: **cell towers** (different towers heard, split 5G/4G/3G/2G, the connected tower and network, signal now and its range, dead spots), **Wi-Fi** (different networks seen, around you now, 2.4/5/6 GHz split, strongest), **Bluetooth** (different devices seen, now, most at once), **GPS** and **radio**, plus the tiles for ground cleared, distance walked, readings and new cells. After you stop, it opens by itself to the last session with the sign-and-submit buttons.
- **Counting without addresses:** to count *different* networks and devices, the scanner mixes each address with a random per-session value and shortens it (`modules/signal-scan`, `anonymous`). The numbers are held in memory only (`src/mapping/sessionStats.ts`), dropped when the session ends, and never saved, shown or uploaded; reports still carry only counts and levels.
- **Smoothness:** the compass heading (about 20 updates a second) lives in its own store so only the arrow and the dot's cone redraw; the session clock is its own component; the fog shape is rebuilt at most about once a second; and the map component is memoised.
- **Signal map:** while you map, each reading is painted as a soft glowing blob where it was taken, so a walk becomes a heat trail (`src/mapping/signalLayer.ts`). Chips choose what to tint by: Cellular (red is no signal, green is strong), Wi-Fi networks, Bluetooth devices, or Off, with a legend. The blob keeps the same size on the ground at every zoom. It is drawn under the fog, so it only shows on mapped ground. This data stays on the phone.
- **Chests** appear on the map as glowing pins, but **only while mapping is on**. The nearest one is shown at the top of the screen, under the signal chips, as an arrow that points toward it (turning with the phone's compass) and its distance. Tapping it opens the chest; within 60 m a camera button opens AR. There is no line drawn to the chest and no separate Chests tab.
- If the map cannot load, the screen says so and offers Retry, instead of staying blank.

Reporting cells (about 100 m, `h120`) are a separate, coarser grid used for reports and chests. The fog and signal data never leave the phone.

## Finding and opening chests in AR

When you are within 60 m of a chest, the camera button next to the nearest-chest indicator, and the chest sheet, offer **Find it in AR**. This opens the camera with a 3D treasure chest drawn where the chest really is, held still in the world as you turn, with a column of light so you can spot it from across a street.

- **How it stays put** (`src/ar/`): a small native piece (`modules/signal-scan`, `startOrientation`) streams the phone's orientation from Android's rotation-vector sensor (the accelerometer, gyroscope and magnetometer fused, the same one AR apps use) with the magnetic declination for the current position. `orientation.ts` turns that into a camera direction in true north and places the chest along the bearing to its real position. This is "sensor AR": it uses compass and GPS, not camera tracking of surfaces, so it is only as steady as they are.
- **Drawing:** `chestScene.ts` builds the chest from shapes and generated textures (no model files): wood, iron straps, gold corners, studs, a lock, a domed lid, a glowing ground ring and a light beam. It runs on `expo-gl` with `three`. The camera picture comes from `expo-camera`.
- **Distance:** the chest is drawn at its real distance, but never closer than 4 m (so it stays big enough to tap) or farther than 40 m (so it stays in view). GPS error is smoothed over about half a second.
- **Opening:** tap the chest. It opens only when you are within 30 m *and* have the readings the chest needs (the same rules as opening it from the card). The lid lifts, light and gold coins burst out, and then the wallet signs and the submission goes to review. If you tap too early, the screen says what is missing.
- **Exact positions:** chests made with `create-chest` or the requester console store exact coordinates, so AR and the map put them where requested. Older chests fall back to the centre of their 100 m cell.
- **Fallbacks:** without camera permission the screen asks for it. If the phone has no rotation sensor, or 3D cannot start, it says so and offers a plain "Open chest" button with the same rules.
- **Not verified:** the sensor stream, the camera overlay, `three` on `expo-gl`, and the steadiness of the chest have not run on a phone. The 3D look was checked by rendering the same scene in desktop Chrome, and the maths (heading, tilt, declination, projection) is unit tested.

## How a report travels

1. **Mapping session** (Map tab, Start mapping). A foreground service with a visible notification runs. Every ~20 s the phone reads signals and the latest GPS fix. A reading is kept only if the fix is accurate (50 m or better), not flagged as a mock location, recent, and not implausibly fast, and not inside the user's home exclusion zone (`src/mapping/session.ts`).
2. **Aggregation.** Readings are folded into per-cell, per-15-minute buckets of counts and levels (`src/mapping/aggregate.ts`). The cell is a hex ~120 m (projected) across (`src/mapping/hexGrid.ts`). Exact times, the trail, and the fog map stay on the phone.
3. **Report.** Stopping builds a report: node address, device model, buckets, plausibility counters (`src/reports/report.ts`). Chest claims and satellite-pass receipts use the same envelope.
4. **Signing.** The connected wallet (Seed Vault on a Seeker) signs `"azimuth-report-v1\n" + canonical JSON` through Mobile Wallet Adapter (`src/wallet/signReport.ts`).
5. **Verification** (`server/lib/service.js`, `rules.js`, `orbit.js`). The verifier checks, in order: signature and hash; duplicate; rate limit; node eligibility (optionally a Seeker Genesis Token, one SGT per node); plausibility of every bucket and counter; for pass receipts, the satellite's orbit; for chest claims, the chest's rules (place, time, readings, kind-specific evidence).
6. **Reward accounting.** Accepted reports earn a small, capped subsidy for cells new to the network, and the chest reward if one was claimed. These are rows in a ledger.
7. **Payout.** If a chest has an on-chain bounty attached, `onchain/scripts/settle.ts` pays pending claims from escrow and records the transaction signature back in the verifier.

## Review queue and weekly payout (Supabase)

An alternative to paying from on-chain escrow: a person approves rewards and a script pays them once a week.

1. **Set up once.** Create a Supabase project and run `server/supabase/schema.sql` in its SQL editor. It creates `reports` and `rewards` tables, locks them with row-level security so the app's public key sees nothing, and adds a `weekly_payable` view.
2. **Run the verifier with** `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` (the service-role key, kept on the server only). Each accepted report is copied to `reports`, and the rewards it earned are added to `rewards` as `pending`. If Supabase is unreachable, the copy waits in a local queue and is retried every minute, so nothing is lost.
3. **Review in the dashboard.** Open the `rewards` table and set `status` to `approved` or `rejected`. Open the matching `reports` row to see what was submitted. A paid reward can never be changed again (a database trigger enforces it).
4. **Pay weekly.** From `onchain/`:
   ```bash
   SUPABASE_URL=... SUPABASE_SERVICE_KEY=... RPC_URL=... \
   PAYOUT_MINT=<token mint> TREASURY_KEYPAIR=./treasury.json \
   npx ts-node scripts/payout.ts                 # dry run: prints who gets what
   PAYOUT_CONFIRM=yes PAYOUT_MAX_TOTAL=100 ... npx ts-node scripts/payout.ts   # sends
   ```
   It adds up approved rewards per wallet, refuses to send more than `PAYOUT_MAX_TOTAL` or more than the treasury holds, pays in batches (creating token accounts as needed), then marks the rewards `paid` with the transaction signature. Each sent batch is written to a local journal first, so if marking fails after the money went out, the next run only repeats the marking and never pays again.
5. **Deleting data.** A signed deletion request blanks the stored reports in Supabase as well (rewards and totals stay).

In this mode you are the custodian: people rely on you to review and to pay. Say so in the app and listing.

## Direct mode: no server (Supabase only)

The app can talk straight to Supabase with the **publishable** key. Nothing runs all the time; a few scripts run when you choose.

**Set up once:** run `server/supabase/schema.sql`, then `server/supabase/schema_direct.sql`, in the Supabase SQL editor. Build the app with `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_KEY` (see `.env.example`).

**What the public key can do** (enforced by the database, not by the app): read open chests; insert a report with only four columns (hash, wallet, type, body), limited in size and rate; file a signed deletion request; look up a wallet's reward totals. It cannot read reports or rewards, change anything, or delete anything.

**What happens to a submission (manual approval)**
1. The app signs the report and inserts it. The user sees "Submitted for review", not "Accepted". Nothing is checked or paid yet.
2. A person reviews it in the **admin portal**: `cd server && npm run admin`, then open `http://127.0.0.1:8788` and sign in with `ADMIN_PASSWORD`. The portal runs on your computer with the secret key; the page in the browser never sees that key and only talks to the portal. For each waiting submission it shows the wallet, phone, readings, speed, a map of the cells, and the automatic checks (signature, plausibility, chest rules, orbit) **as advice**, plus what approving would pay.
3. **Approve** creates the rewards already marked `approved` (ready for the weekly payout), makes the cells known to the network, and fills the chest. A submission that fails the automatic checks cannot be approved (it can only be rejected), so one wrong click cannot pay an implausible report. **Reject** needs a reason, which is stored with the report.
4. Until you decide, the submission earns nothing. The user's Profile shows how many submissions are waiting and the approved and paid totals.
5. Weekly, run the payout script (`onchain/scripts/payout.ts`) to pay the approved rewards.

Housekeeping is separate and does not decide anything: `npm run review` syncs chests and carries out signed deletion requests. `npm run review -- --auto` exists if you ever want rule-only approval; it is off by default.

**What still needs something running**

| Job | How often | How |
|-----|-----------|-----|
| Approve or reject submissions | whenever you like | `npm run admin` in `server/`, then the browser |
| Deletion requests and chest sync | daily, or with `--watch` | `npm run review` in `server/`. Keep `review.db` between runs |
| Create chests | when you want one | `npm run create-chest -- --title ... --lat ... --lon ...` or add a row in the dashboard |
| Pay approved rewards | weekly | `onchain/scripts/payout.ts` |
| Refresh orbit data for the satellite check | occasionally | `npm run update-tles` |

The admin portal listens only on this computer. If you ever host it, put HTTPS in front first. The page loads no third-party scripts, and report contents are only ever shown as plain text so a malicious report cannot run code in the portal.

**Trade-offs of direct mode:** the public key means anyone can insert report rows (the database limits size and rate, but a determined flood is possible), nothing is checked until review, and the "new cell" subsidy is decided at review time. The Seeker check, instant accept/reject answers and live earnings of unreviewed reports are not available.

## Where Solana is used

| Use | Where | On-chain? |
|-----|-------|-----------|
| Wallet connection and identity | Mobile Wallet Adapter, `src/wallet/` | The wallet address is a Solana account |
| Signing reports | Seed Vault key signs each report (ed25519) | Signature is checked off-chain by the verifier |
| Proof it is a Seeker, one device per node | Seeker Genesis Token lookup over Solana RPC, `server/lib/seeker.js` | Reads the chain |
| Paying people | Weekly SPL token transfers (`onchain/scripts/payout.ts`) or the escrow program | Yes: this is where value moves |
| Requester-funded escrow | `onchain/programs/azimuth_bounty` | Yes, optional; unused in the Supabase flow |

Not on-chain: the measurements, reports, approvals, fog map and the coverage atlas. They live on the phone and in the verifier's database. Putting the raw data on-chain would be costly and would publish places, so the design keeps it off. A cheap way to add tamper-evidence later is to publish a weekly Merkle root of the accepted report hashes on-chain; this is not built.

## Running it

```bash
# App (development build, not Expo Go)
npm install
EXPO_PUBLIC_VERIFIER_URL=http://<your-computer>:8787 npx expo run:android

# Verifier
npm run server                       # node server/index.js, port 8787, db azimuth.db
node server/tools/update-tles.js     # refresh Meteor TLEs used by the pass check
# Requester console: http://localhost:8787/console

# Tests
npx jest                             # app
npm run test:server                  # verifier
cd onchain && npm install && npm test   # escrow program (starts a local validator)

# Verify a signed report by hand
node server/lib/verify-report.cjs report.json
```

Server environment variables:

| Variable | Meaning |
|----------|---------|
| `PORT`, `DB_PATH` | listen port (8787) and SQLite file (`./azimuth.db`) |
| `REQUESTER_KEY` | API key needed to create chests. Unset means anyone can (development only) |
| `OPERATOR_KEY` | enables the settlement endpoints used by `onchain/scripts/settle.ts` |
| `REQUIRE_SEEKER=1`, `RPC_URL` | accept only wallets holding a Seeker Genesis Token (mainnet RPC) |
| `SONDE_REGION="lat,lon,radiusKm"` | turn landed radiosondes near a region into recovery chests |
| `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` | copy accepted reports and rewards to the Supabase review queue |

## Verified, and what is not

**Verified by tests in this repository**
- App logic: 335 Jest tests (hex grid, aggregation, session rules, radio analysis, report building and signing format, wallet store with a mocked wallet, existing radio and capture suites).
- Verifier, review job and admin portal: 65 tests, including the independent signature check, tampering and replay, plausibility limits, rate limits, daily subsidy cap, SGT gate and one-SGT-one-node rule, each chest kind, orbit physics against real Meteor TLEs, sonde selection and claims, data deletion, and the HTTP API.
- Escrow program and payout script: 15 tests on a real local validator. Escrow: full escrow on creation, pay-once per node, verifier-only settlement, no overpay, no wrong-owner payout, no payout after expiry, refund only after expiry plus grace, the settlement script, and the weekly payout (grouping, dry run, spending cap, treasury balance check, once-only payment, and recovery when marking fails after sending).
- Builds: the app builds as a debug APK with both native modules; the escrow program builds for SBF.
- Live data: the sonde sync was run against SondeHub's public API and produced chests from real landed balloons.

**Not verified: needs a Seeker and real-world testing**
- Mobile Wallet Adapter connect, `signMessages`, and the Seed Vault behaviour have never run on a device. They are tested only against a mock.
- The native scanner has been compiled but not run: cellular, Wi-Fi throttling, Bluetooth, GNSS values, battery cost, and behaviour with the screen off need testing on real hardware.
- Dongle-assisted mapping (radio sweep, Meteor and sonde probes) and the auto-gain have not run on hardware. The Meteor/sonde thresholds are first guesses.
- No real satellite pass has been recorded.
- Seeker Genesis Token checks run against a fake chain in tests; the real RPC path is untested.
- The escrow program has had no external audit and is not deployed to devnet or mainnet.
- The Supabase push has been tested against a simulated Supabase, not a real project: the SQL has not been run, and the real REST calls and the payout against a live token are untested. Try it on devnet first.

**Known weaknesses by design** (see DEPIN_DESIGN.md section 5)
- The verifier checks plausibility, not truth. A modified app can invent readings that look plausible. Venue-tag, sonde-frequency and Meteor checks raise the cost, but all of them can be faked with public information.
- One verifier is trusted. The escrow limits what it can do (it cannot take funds, double-pay, or exceed the funded fills), but it decides who is paid.
- Reward amounts are placeholders. Demand is unproven; talk to real requesters before relying on any of this.

## Units, arrow accuracy, sheet gesture and zoom (2026-10-04)

- **Units** (`src/units/units.ts`): Settings > Units offers Automatic, Miles & feet, Kilometres & metres. Automatic reads the phone's region (`I18nManager.localeIdentifier`) and uses miles and feet in the US, Canada, the UK and a few others, kilometres and metres elsewhere. Applies to chest distances, the compass pill, AR text and range limits, session distance and area (acres / mi²), and satellite range and altitude. The choice is stored on the phone (MMKV).
- **Arrow**: drawn as an SVG dial (tip straight up), turns by `bearing - heading` and glides the short way round. Heading comes from the native rotation-vector sensor, corrected to true north. The native module now also reports the sensor's own accuracy status; when it is low or unreliable the pill asks for a figure-8 wave of the phone. Not yet checked on a real phone.
- **Mapping sheet**: drags from anywhere (header always; body only when scrolled to the top or not fully open).
- **Map zoom**: starts at zoom 17 once both a fix and the map exist; the location button flies to you on the first press.
- **Dongle at start**: pressing Start mapping now connects a plugged-in RTL-SDR first (`ensureDongle`, 20 s allowed for the Android USB prompt; mapping carries on without it if there is none). If it was missing at start, a later radio reading tries again, at most every 3 minutes. A radio reading about once a minute sweeps five 2.4 MHz windows (FM 98 MHz, Meteor-M 137.5 MHz covering 137.1 and 137.9, UHF 462.6, 751 and 945 MHz cellular bands) at a fixed 28 dB gain and stores the combined level; the Meteor check (is a Meteor-M LRPT signal heard, which only happens during a pass) comes from the 137.5 window.
- **Radio coverage layer**: a Radio chip appears next to Cellular / Wi-Fi / Bluetooth once a dongle is connected or radio readings exist. It tints the map by the overall radio level measured there, in dB below full scale (dark = quiet, about -45 dBFS; yellow = strong, about -20 dBFS). The scale is a first guess and needs tuning against a real dongle.

## Keeping map progress (2026-10-04)

Progress = the cleared fog (`explored`), visited cells and the signal map, kept by MMKV under the name `azimuth-mapping`.

1. **Android automatic backup** (`plugins/withAzimuthBackup.js`, `plugins/backupRules.js`): a config plugin sets `allowBackup`, `fullBackupContent` and `dataExtractionRules` so Google's backup and device-to-device transfer copy only `files/mmkv/azimuth-mapping` (and its `.crc`). The wallet session and the backup key live under other MMKV names and are excluded. The `android/` folder is generated and git-ignored, so the plugin is the source of truth (it was also applied to the current `android/`). Needs a rebuild; not yet checked on a device (Android decides when it backs up; the user needs backup turned on and the same Google account on the new phone).
2. **Encrypted wallet-keyed sync** (`src/backup/`, Settings > Back up your map): the wallet signs a fixed message (twice, once, to confirm the signature is deterministic); HKDF turns the signature into a 32-byte key and a 16-byte lookup tag. The progress is gzipped (`fflate`), sealed with XChaCha20-Poly1305 (`@noble/ciphers`) and stored in Supabase table `backups` (run `server/supabase/schema_backup.sql`). Supabase holds only ciphertext. On a new phone, turning backup on with the same wallet derives the same key, fetches the newest row and merges it (cells are only added; for a signal cell the copy with more readings wins). It uploads again when something is new, and syncs by itself when a mapping session ends. The key is kept in its own MMKV store (`azimuth-backup`), not in the backed-up files.
   - Safety against strangers: rows are insert-only for the public key; fetching needs the secret tag; pruning (keep the newest 3) only touches rows with the same wallet and tag; per-wallet and global rate limits; anything that does not decrypt is ignored. "Delete my data" also erases the wallet's backups (`eraseNode`).
   - Not verified on a device: the MWA signature being deterministic on a Seeker's Seed Vault (the app refuses to enable backup if two signatures differ), and the Supabase function and policies (the SQL has not been run yet).

## Session history (2026-10-04)

When a mapping session stops, a summary (`SessionRecord`: date, duration, distance, area cleared, new cells, readings, towers / Wi-Fi / Bluetooth counts, average radio level) and the list of fog cells it cleared are saved on the phone (`sessions`, `session-cells:<id>` in the `azimuth-mapping` store). Sessions with no readings and no cleared fog are not kept. No route is stored, only the cleared cells. The list shows under the Last session card when the panel is swiped up and mapping is off. Tapping a session outlines its cleared area in amber, fits the camera to it and closes the panel; a chip at the top-left puts it away, and starting a new session also does. Deleting a session removes it from the list (the fog stays cleared); "Erase fog map" also clears the history. History is part of the encrypted backup (`sessions`, `sessionCells` in the snapshot; older backups without them still restore). Sessions mapped before this change are not listed, because their data was not kept.

- **Last session after a restart**: the panel's "Last session" card now comes from the history, so it is there after the app is reopened. Sessions mapped before history existed are rebuilt once at launch from the fog map's timestamps (cells cleared within 30 minutes of each other are one session; groups under 20 cells are ignored); they show date, duration, area and cleared cells only, marked "Rebuilt from your fog map". A finished session's unsent report is also saved (`pending`) and restored at launch so Sign and submit still works after the app is closed; it is cleared once the report is sent, and when a new session starts.

- **Test chest** (Settings > Test chest): "Drop a test chest here" places a chest exactly at the phone's position (in AR it is drawn in front of you, in the direction you were facing when you dropped it), held only in memory (`useChests.addTestChest`, spec flag `test: true`). It needs mapping on and one reading, needs no wallet, and opening it finishes locally ("Nothing was submitted") instead of sending a report. It survives a chest refresh, and is gone after an app restart or "Remove test chests".

- **Steady AR chest** (2026-10-04): the chest is on the ground (camera height 1.3 m), drawn larger (scale 1.9, about 1.9 m wide) and does not move: no bobbing, and it no longer turns to face the camera every frame (it faces you when first placed and stays). The phone's GPS goes through an accuracy-weighted filter (`src/ar/stabilize.ts`) and, while the filtered position says you are standing still, a change of under 2.5 m (`HOLD_M`) does not move the chest at all. When you are closer than the nearest drawing distance (5 m) the chest is drawn straight ahead of where the camera pointed when AR opened and stays there; the test chest has a "Put it in front of me" button to redo that. Not yet checked on a phone; a held phone drifts a little with the compass, so a small slow shift is still possible.
- **Opened chests and amounts** (2026-10-04): once a chest is opened and accepted (`useChestClaim` sees a finished, accepted result), `useChests.markOpened` removes it from the map and list and remembers its id on the phone (`openedChests`, last 500), so a refresh from the network does not bring it back before the review has caught up. No chest shows a USDC amount anywhere (map pin, top pill, list, chest card, AR bar, pass receipt); the amount is still stored in the data and shown in Profile as the wallet's earnings.

- **Online radio** (Radio tab > Online, 2026-10-04): tune an FM frequency (87.5 to 108.0 MHz, 0.1 steps, +-0.1 and +-1 buttons, or type it) and hear a station over the internet. The frequency is looked up in the free Radio Browser directory (`src/radio/online/radioBrowser.ts`, several servers tried in turn, no account): it lists stations by name, so the search is for names that contain the number ("103.5", "103,5", or "98" / "98.0" for a whole number), keeping only exact matches, own-country stations first, then by votes. The best match plays (`expo-audio`, `useOnlineRadio`); other matches are listed to switch to; there is also a search by name. It cannot find a station that does not put its frequency in its name. Playback stops when you press Stop or start a dongle listen; foreground only (it stops with the app), no lock-screen controls. Many stations are plain http, so `plugins/withCleartextAudio.js` allows cleartext traffic (the rest of the app uses https). Needs a rebuild (new native package). Not yet heard on a phone.
- **Online signal bars**: Online mode shows 64 bars like the dongle spectrum, but of the sound being played: `expo-audio` gives out the PCM samples of the playing stream (`setAudioSamplingEnabled`, an undocumented API), which are windowed and run through an FFT (`src/radio/online/audioSpectrum.ts`) into bars that rise fast and fall slowly, low pitch on the left. On Android this reads the sound through a `Visualizer`, which only works if the app holds the microphone permission (RECORD_AUDIO, added by the expo-audio plugin), so the bars are opt-in: until the user taps "Show signal bars" the radio plays and the card explains why. Nothing is recorded; the privacy page says so. If sampling is unsupported it says so instead of drawing fake bars. Not checked on a phone (the Visualizer path and the sample rate it gives are unverified).
- **Online radio fixes**: on Android `expo-audio`'s `player.remove()` only forgets the player and does not stop the sound, so Stop and retuning left the old stream playing (and a new one played over it). Releasing a player now pauses it and mutes it first, then removes it (`releasePlayer`), and stations are released before a new one starts. The signal bars now fall back to a simulated moving display (labelled SIMULATED) when the real sound cannot be read (no microphone permission yet, or unsupported); "Use the real sound" asks for the permission and switches to real bars when samples arrive.
- **Local online radio**: Online mode now knows where you are (last known position, country from the phone's geocoder or its region setting, cached 5 minutes). Station rows carry the directory's `geo_lat` / `geo_long`; tuning a frequency ranks stations by distance (known positions first, nearest first), then country, then votes, so "103.5" plays the one in your own area. A **Near me** card lists stations within about 120 km (`searchNearby`: the directory has no distance query, so the country's stations that have a position are fetched and filtered on the phone), with the distance shown in your units. Without location permission it still tunes by votes and says "Allow location". Stations without a position in the directory cannot be placed.
- **FM from your own country** (online radio): tuning a frequency asks the directory for stations of the listener's country only (`countrycode`, and filtered again on the phone), nearest first, and lists all of them. FM frequencies are reused between countries, so a 98.7 elsewhere is not the one you can tune. The country comes from the phone's geocoder; without one it is the phone's region setting checked against the position (`guessCountry`: a US or Canada setting while standing elsewhere, or another setting while standing in the US or Canada, is treated as stale). Stations from other countries are never shown: if the country has nothing on that frequency the screen says there is no station, and if the country cannot be worked out at all (no location, no geocoder, and a region setting that disagrees with the position) nothing is tuned and the screen asks for location. Name search is limited to the country the same way.
- **Dial follows the playing station**: whichever station starts (from the tuned list, Near me or a name search), the frequency, dial and bar move to the frequency in its name (`frequencyFromName`; whole numbers count only with FM or MHz after them); a station with no frequency in its name leaves the dial alone. The station list keeps its own title (`listTitle`) so it still says which frequency or search it came from.

## Sonde tracking, mapping buttons and profile (2026-10-05)

- **Sondes** (Satellites tab > Sondes): lists radiosondes heard by SondeHub within 300 km (`api.v2.sondehub.org/sondes?lat&lon&distance`, no key), ordered for hunting: landed first (silent 10+ minutes, below 3000 m, descending), then coming down, then climbing, nearest first; entries over 72 hours old are dropped, and ones that went quiet high up are hidden. Each opens a hunt screen: an arrow and distance to the place to head for (the last position once landed; for one still falling, an estimated landing carried along its heading for the time it has left, a rough guess because wind changes with height), details, "Get directions" (opens a maps app via a geo: link), Track (kept in the list, starred, and remembered if it drops out of the search), Share, and "Tune the dongle" to its frequency when the dongle is connected. The list refreshes every 30 seconds on the hunt screen. Not yet verified against the live API on a phone; predictions from SondeHub are not used.
- **Start/Stop mapping button**: a gradient button (teal to blue to start, red with a pulsing marker and LIVE tag to stop), spinner while working.
- **Profile**: the .skr name (Seeker ID, looked up on mainnet with `@onsol/tldparser`: the main domain if it is .skr, otherwise the first .skr name; remembered for a week, a "no name" answer for six hours) is the user name, with the address under it; the "What's coming" list was removed. `package.json` has an `overrides` entry so the library's strict `buffer` peer requirement resolves to the app's version.
- **Driving leaves a solid road** (2026-10-05): the fog used to be cleared only in a circle around each GPS fix, and fixes came every 5 s or 5 m, so at car speed the circles were far apart and the map looked like dotted circles. Now the phone asks for a fix every second (or 3 m), and each fix also clears the fog along the straight line from the previous fix (`pointsAlong`, a point every 20 m; not across gaps over 2 km or 2 minutes, which are signal losses). Readings for the signal map are also taken more often when moving fast (every 10 s above 3 m/s, every 6 s above 10 m/s), so the heat trail has fewer gaps. Costs to watch: more battery from the faster GPS, and a long drive clears a lot of 5 m fog cells (about 300 per 60 m circle), which makes the stored map and the fog redraw bigger.
- **You on the map** (2026-10-05): the dot is now a drawn character (`PersonArt`, `PersonMarker`): a little radio explorer in a cap and headphones with a backpack antenna, standing on a glowing ground ring with its feet on the exact position. Still, it breathes; above 0.8 m/s it strides (two stride frames swapped every 300 ms, with a bounce); above 6 m/s (`activityFor` in `headingStore`, speed from the GPS fix) it sits in a small car. A soft beam on the ground shows which way the phone faces. The artwork was checked in a browser render, not yet seen on a phone.
- **One unit setting everywhere** (2026-10-05): the area shown on the Profile (Explored) and on the map (cleared area) was always in km² / m² while distances followed the setting; `formatArea` now goes through `areaParts` like every other area, so miles setting gives mi² or sq ft and the metric setting gives km² or m², with thousands separated. A balloon's height uses `heightParts` (m or ft, never km or miles), and the Sondes screens' literal "300 km" and "few hundred metres" text now follow the setting. Every distance, area, height, speed and range in the app now comes from `src/units/units.ts`.

## Challenges / Quests (2026-10-10)

- **Quests tab and challenges**: five seeded challenges (scan 30 minutes, find 20 new cells, explore new ground weekly, catch 3 satellite passes, open your first chest) live in the Supabase table `challenges`. Edit them in the Supabase table editor; the app fetches them and the server caches the list for up to 60 s. Validation: whole reward 1..100, goal > 0, known period, metric and go_tab; invalid rows are ignored.
- **Claim flow**: the app tracks progress from local sessions plus verified passes and chests. Claim signs a `challenge-claim` once and the card shows "Claim pending" (the app re-checks every 5 s until it is paid or rejected). The portal's 5 s timer or the "Check challenge claims now" button settles it: the server counts the wallet's approved reports and new-cell reward rows in the UTC period, and if that is short it also counts the wallet's submitted-but-unreviewed reports that pass the automatic checks (for new cells only the single best such report counts, so repeating a walk cannot add up). Then it pays AZMTest kind 3 with on-chain hash `sha256('challenge:id:period')`, so each period pays once. Sessions that were never submitted are invisible to the server, so the claim is rejected with a message to submit them first. Claims wait while the portal is off or no chain is configured. Ruling: a quest can pay out on a report that is later rejected by a person; amounts are small and capped on-chain.
- **SQL to run**: `server/supabase/schema_challenges.sql`, after `schema_azm.sql`.
- **Known limits**: the app and server count progress on different clocks (session start vs review time), so a card can say Ready and the server reject with the numbers. The weekly 70-cell goal counts cells on the projected map grid. The sonde challenge is deferred.
- **Verified**: server and app tests. **Not verified**: the tab on a phone, the Seed Vault claim prompt, the live devnet payout, behaviour near UTC midnight.
